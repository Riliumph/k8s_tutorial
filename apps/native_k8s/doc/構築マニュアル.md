# 構築マニュアル

3台のdebianコンテナをメタルサーバーに見立ててクラスターを構築する手順。  
コンテナ特有の`systemd`の無効化などがあり、必要要素を一つずつ確認する。

## リソースの管理について

`kubelet`と`containerd`は両方が`cgroup`を用いてリソースを管理する。  

> cgroupについては[ここ](./kernel/cgroup.md)

今回はsystemdで制御を行う。

### systemdの有効化

その場合、`CMD["/bin/bash"]`だとPID=1がbashになってしまいsystemdが機能していない。

必要があれば、dockerfile内のaptでsystemdをインストールしよう。  
それから、dockerfileの末尾を`CMD["/sbin/init"]`に変更する。  
`ps aux`してみて、PID=1が`systemd`であること。`contaienrd`も起動していることを確認する。

## containerdの設定

`containerd`の設定を確認する。

```console
root@k8s-master:/# grep -n 'SystemdCgroup' /etc/containerd/config.toml
125:            SystemdCgroup = false
```

これが有効になっていないと`containerd`はリソースチェックが行えず、分裂することが出来ない。

> sedで編集するのは有り得ないので設定ファイルをCOPYする。

この設定が有効になれば、`containerd`は`systemd`を介して`cgroup`を使うことが出来る。

## ノードネットワークの設定

### L3ルーティング機能の可否

Linux KernelがパケットをL3ルーティング転送できるかを確認する。  

> ルーター的なアプリケーションがパケットを受けて別のところへ転送するのはアプリケーションとして自由だ。  
> この設定が有効じゃないとアプリケーションの転送も拒否されるとかではない。  
> あくまで、Linux公式の転送機能が有効になっているかを確かめる。

```console
$ docker compose exec -it k8s-master bash
root@k8s-master:/# sysctl net.ipv4.ip_forward
net.ipv4.ip_forward = 1
```

この転送機能がk8sにおけるPod間転送やCNIなどを構成してくれる。

### L2ルーティング機能の可否

> `br_netfilter`については[ここ](./kernel/br_netfilter.md)

モジュールのロード状況を確認する。

```console
# lsmod | grep br_netfilter
Module                  Size  Used by
br_netfilter           28672  0
bridge                286720  1 br_netfilter
```

どうやらロードされているらしい。
今はWSL2->devcontainer->Dockerの流れで立ち上がっているため、コンテナのLinux Kernelは一番底であるWSL2のLinux Kernelを使っている。  

もし、コンテナ環境であればホストのKernelにロードされることに注意しながら以下を実行する。

```console
root@k8s-master:/# modprobe br_netfilter
```

このコマンドは、今の起動でのみ有効なモジュールロードであることにも注意したい。  
もし、専用環境を構築していて、電源再起動時に自動でモジュールがロードされるように設定を永続化したい場合は[ここ](./kernel/module-load.md)を参照すること。

次に、Kernel parameterを確認する。

`br_netfilter`がロードされていることが分かったが、正しい設定がされているかを以下のコマンドで調査する。  
このパラメータは`br_netfilter`が提供するsysctlである。

```console
root@k8s-master:/# sysctl net.bridge.bridge-nf-call-iptables
net.bridge.bridge-nf-call-iptables = 1
```

## CRIの疎通確認

> Container Runtime Interface  
> コンテナを作ったり、イメージを取得したり、コンテナを停止したり……  
> といった処理をcontainer runtimeに依頼するインターフェイス。  
> k8sではkubeletが実行・送信する。

OSの土台は形になったので、次は疎通確認を行う。  

念のためプラグインを確認しておく。

```console
root@k8s-master:/# ctr plugins ls | grep cri
TYPE                            ID                       PLATFORMS      STATUS    
io.containerd.grpc.v1           cri                      linux/amd64    ok     
```

containerdがCRI持っているので、`kubelet`は問題なく命令を出せそうですね。

## kubeadmの挙動確認

`kubeadm`はこれらを`systemd`サービスとしてインストールするわけではない。

`kubeadm`はmanifestを作り、`kubelet`を使ってstatic podとして`Control Plane`を起動する。

```console
root@k8s-master:/# kubectl get nodes
NAME         STATUS     ROLES           AGE   VERSION

```

設定したら`kubectl`が使えるようになった。

ただし、`STATUS=NotReady`となっているので、これを直そう。

### CNI構築

なぜ`STATUS=NotReady`になっているのか？  
これは[ネットワークプラグイン](./k8s/cni_plugin.md)が入っていないためPod同士がルーティングを行えずPod間通信が出来ないからだ。  
これを解決するにはネットワークプラグインを導入してCNIをきのうさせなければならない。  

最初なので`Flannel`で行う。  
`Flannel`の定義をAPI Serverへ登録し、DaemonSetを作成する。

```console
root@k8s-master:/# kubectl apply -f https://github.com/flannel-io/flannel/releases/latest/download/kube-flannel.yml
namespace/kube-flannel created
serviceaccount/flannel created
clusterrole.rbac.authorization.k8s.io/flannel created
clusterrolebinding.rbac.authorization.k8s.io/flannel created
configmap/kube-flannel-cfg created
daemonset.apps/kube-flannel-ds created
```

`Flannel`が各ノードで起動したかは分からないので、一旦全ノードを調べる。

[失敗する場合はこちら](./k8s/cni構築.md)

### PodにCIDRを設定する
